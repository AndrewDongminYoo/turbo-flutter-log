# turbo-flutter-log v1 — Implementation Plan

Status: `planned`
Date: 2026-08-02
Spec: `docs/specs/2026-08-02-v1-design.md`
Audit being remediated: `docs/notes/2026-08-02-current-state-audit.md`

## Sequencing rationale

The corrupted patterns documented in the audit are currently harmless because they match nothing.
Repairing them without a provenance marker and a language guard already in place would turn a dead command into one that deletes hand-written `print()` calls from arbitrary files.
Phase 3 therefore lands the marker, the guard, and the repaired patterns together, and no phase before it touches the existing bulk commands.

Phases 1 and 2 build the pure core first, because those modules carry the logic that the shipped defect lived in and are the only ones testable without an editor.

Each phase is one commit.
A phase is not done until its verification command has been run and passed.

## Phase 0 — Test harness

The project can currently only run tests inside the extension host, which is why the pure logic has no coverage.

- Add `src/test/unit/` for `vscode`-free tests and keep `src/test/suite/` for extension-host tests.
- Add `npm run test:unit` → `tsc -p . --outDir out && mocha 'out/test/unit/**/*.test.js'`.
- Keep `npm test` as the `vscode-test` integration run and add `npm run test:all`.
- Delete the scaffold assertion in `src/test/extension.test.ts`.

Verify: `npm run test:unit` runs without launching VS Code, and `npm test` still runs the extension-host suite.

Deviations recorded during execution:

- `src/levels.ts` and its unit test moved up from Phase 1. Mocha exits non-zero when a glob matches no files, so proving the runner works needs one real subject; `levels.ts` is the smallest pure module in the design.
- The scaffold assertion was replaced rather than merely deleted, with a test that every contributed command is actually registered. An empty `src/test/suite/` would make `.vscode-test.mjs` fail to collect.
- `@vscode/test-electron` bumped `2.5.2` → `3.1.0`. The 2.x line resolves the macOS binary as `Visual Studio Code.app/Contents/MacOS/Electron`, but VS Code 1.131.0 ships it as `MacOS/Code`, so the runner died with `spawn ... ENOENT` before any test ran. `@vscode/test-cli` was deliberately left at `0.0.10`: it resolves `@vscode/test-electron` from the project directory rather than depending on it, so it needed no bump, and `0.0.15` would have pulled mocha 11 and with it `diff@7.0.0`, re-opening GHSA-73rr-hh4g-fpgx.

## Phase 1 — Pure core

Test-first. Write the assertions from the spec's Testing section before the implementation.

- `src/levels.ts` — `logLevel` → `package:logging` integer. Six mappings.
- `src/config.ts` — a `TurboConfig` interface plus a pure `resolveConfig(raw)` that applies defaults and validates. The `vscode.workspace.getConfiguration` read stays in a thin separate function so `resolveConfig` is testable.
- `src/statement.ts` — segment assembly and call emission for all three `logFunction` values, quote fallback, simple versus complex interpolation.
- `src/marker.ts` — the single turbo-log pattern, with regex-metacharacter escaping of the configured marker.

None of these four files may import `vscode`.

Verify: `npm run test:unit` — all unit tests pass, including a `marker.ts` test asserting that the pattern matches `statement.ts`'s own output for every `logFunction`, in both commented and uncommented form, and does not match `print('hello')`.

## Phase 2 — Analysis server access

- `src/symbols.ts` — wrap `vscode.executeDocumentSymbolProvider`; walk `children` depth-first for the innermost containing symbol; find the nearest class-like ancestor. Return `undefined` rather than throwing when no provider answers.
- `src/target.ts` — wrap `vscode.executeSelectionRangeProvider`; resolve the target expression from a selection, or from the cursor when the selection is empty; return the enclosing statement's range so the caller knows where the statement ends.
- Session-scoped "Dart extension not available" warning, shown at most once.

Verify: unit tests over chains captured from a running `dart language-server`.

The risk is resolved, and the fallback is not needed.
A probe drove `dart language-server --protocol=lsp` directly over stdio and asked for `textDocument/documentSymbol` and `textDocument/selectionRange`.
Dart returns hierarchical `DocumentSymbol[]` with children, and a fine-grained range chain — for a cursor on `user` in `final name = user.profile.name;`:

```plaintext
user → user.profile → user.profile.name → name = user.profile.name → final name = ... → ...;
```

Deviations recorded during execution:

- `symbols.ts` and `target.ts` are pure and import no `vscode`; the two provider calls moved to `editor.ts`, which holds no decisions. The tree walk and the expression choice are the parts worth testing, and they are now testable without an editor — the same property Phase 1 established.
- The planned extension-host test is not possible: `vscode-test` launches a clean VS Code with only this extension installed, so no Dart language server answers there. Installing the Dart extension plus a Dart SDK into the test host would make the suite slow and dependent on analysis-server startup timing. Instead the seven cursor positions captured from the real server are recorded as fixtures in `src/test/unit/target.test.ts`, and `editor.ts` is exercised by Phase 3's manual verification in a real Flutter file.
- `hasTopLevelStop` treats `=` at bracket depth zero as a stop in every form, including `==` and `=>`. Distinguishing assignment from comparison cost a branch and changed no outcome: for `a == b` the useful expression is an operand, exactly as it is for `compute(p) + 1`.

## Phase 3 — Insert, marker, and guard

This is the phase that makes the repaired bulk commands safe, so it precedes them.

- `src/commands/insert.ts` — rewrite `displayLogMessage`: language guard, multi-cursor, indentation inheritance, insertion after the resolved statement end, all edits in one `editor.edit()`.
- `src/imports.ts` — detect an existing `import 'dart:developer'` and its alias; insert one after the last import when absent; emit in the same edit as the statement.
- Remove `generateLogStatement` and its insert-time timestamp.
- Add the language guard helper and apply it to all five command handlers.

Verify: `npm run test:all`, plus manual insertion in a real Flutter file for each of the three `logFunction` values, confirming the emitted line compiles under `dart analyze`.

## Phase 4 — Bulk commands

- Rewrite `comment.ts`, `uncomment.ts`, `delete.ts` against `marker.ts`.
- Replace whole-document `edit.replace` with per-match `TextEdit`s inside a single `editor.edit()`.
- Refuse to run when `marker` resolves to an empty string.

Verify: extension-host tests — comment then uncomment restores the file byte-for-byte; delete removes only marked logs and leaves a hand-written `print('hello')` in place; every command errors out in a `.ts` file.

The round-trip assertion is the regression test for the shipped defect. It must fail against the current `src/extension.ts` before it passes against the new one.

## Phase 5 — Correct all log messages

- `src/commands/correct.ts` — for each turbo log, re-resolve file name, line number, and enclosing symbol, and rewrite only those segments.
- Register `turbo-flutter-log.correctAllLogMessages` in `package.json`.

Verify: extension-host test that inserts a log, pushes it down by adding lines above it, runs correct, and asserts the line-number segment updated while the payload segment did not.

## Phase 6 — Contribution points

- `contributes.keybindings` for all five commands, per the spec's table, each with `when: editorLangId == dart`.
- `contributes.menus` `commandPalette` entries with the same `when` clause.
- Replace the `logFunction` and `logLevel` configuration entries with the full schema from the spec, including `enumDescriptions`.

Verify: `npm run package` succeeds; the palette shows no turbo commands with a `.ts` file focused and all five with a `.dart` file focused.

## Definition of done

1. `npm run test:all` green, with the comment/uncomment round-trip and the hand-written-log-survives assertions both present.
2. `trunk check --all` clean.
3. `dart analyze` clean on a Flutter fixture project after inserting one log of each `logFunction`.
4. `npx vsce package` produces a `.vsix` with no source or docs inside.
5. This file's status updated to `completed`, and every phase above verified against the code rather than against its checkbox.
